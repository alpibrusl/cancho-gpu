# Benchmark

> Generated by `bench/bench.py` on 2026-11-02 (Apple M4 Max, 64 GiB, macOS 26.2, cancho-gpu `146b4ce`). Every number below was measured on that machine by that script; re-run it to refresh them.

## What is measured

The same raw prompt (about 60 tokens, no chat template), greedy, **128 new tokens**, per runtime: one warm-up run (dropped) then **5 runs**. The cells are the median with the minimum and maximum in brackets.

* **load s**: from starting to being ready to generate (for cancho-gpu: tokenizer, kernel compilation and the weights; for Ollama: the cold load its API reports; for MLX and transformers: reading the checkpoint).
* **prefill tok/s**: prompt tokens over the time to the first generated token (it includes that token's own computation). cancho-gpu takes the prompt eight tokens at a time; the others batch more.
* **decode tok/s**: generated tokens after the first over the time they took, as the runtime or this script measures it (`--timing` for cancho-gpu, MLX's own report, Ollama's `eval_duration`, the difference of two `generate` calls for transformers).
* **peak memory GB**: what the runtime reports (MLX: peak Metal memory; cancho-gpu: the process's resident set, which may not include its Metal buffers). Ollama's API reports none.
* **agrees with reference**: the length of the common prefix of the generated token ids (or, for Ollama, which does not return them, of the text) with the reference runtime's. Different quantisations of one model legitimately diverge.

Runtimes ran one at a time with the others idle; Ollama's models were unloaded first. The GPU is shared with whatever else the machine is doing, which is the main source of the spread. The 1-minute load average at the start was 3.5 (other jobs on this machine; the script refuses to run above `--max-load`, 6 by default, and this invocation overrode it after a probe of plain against speculative decoding repeated within 1%).

**Compare rows within one table, not across invocations.** The spread inside an invocation is small, but two full invocations minutes apart on the same machine differed by up to 1.8x for the same runtime (MLX-LM decoding the 27B: 12.1 tok/s in one, 21.3 in the other; transformers on the CPU: 7.6 and 13.0). Whatever changed between them (clocks, thermal state, what else was resident) was not controlled, so a ratio between two rows is evidence and a number from last week is not.

## Not measured

* Accuracy beyond the agreement column: `scripts/model-check.sh` holds cancho-gpu's logits to transformers'.
* Long contexts: cancho-gpu's context is 256 positions for the 0.5B model and 1024 for the 27B.
* Batched or concurrent requests; energy; a second machine.
* Why the generated texts diverge: greedy decoding over a long open-ended continuation flips at the first near-tie, and runtimes that add in a different order or hold activations in a different precision reach one sooner or later. `scripts/qwen35-check.sh` and `scripts/model-check.sh` compare logits step by step instead, which is the test that a divergence is arithmetic and not a bug.
