A GPU kernel compiler that says what it can do.

lex-gpu's .chx tile-kernel compiler, written in cancho. It checks a typed tile program and lowers it to CUDA C and Metal, byte-for-byte what lex-gpu's Rust emitter writes. It links nothing but libc, and its authority report, checked in CI, names the files it may touch and no network and no foreign code.

Try itSee the evidence
$ cancho-gpu emit gemm_fp4.chx out m=128 n=128 k=64
out/gemm_fp4_128_128_64_128_128_64.cu: 256 threads,
  grid 1x1, 36864 B of tiles
out/gemm_fp4_128_128_64_64_128_32.metal: 256 threads,
  grid 2x1, 12288 B of tiles

$ cancho authority --std src/*.cho
performs: args, err_write, fs_read(""), fs_write(""),
  heap, io_write
never touches: the network, signals, other programs,
  foreign code

The same bytes as the Rust

CUDA C and Metal for 133 emitting cases, identical to lex-gpu's emitter; 26 more refused by both, each with a named rule.

Checked before it is lowered

Every tile is consumed exactly once; bounds, shapes and the threadgroup budget are checked, and a refusal says which rule.

An authority you can read

The report lists exactly what the compiler may do, and the gate fails if it widens. The one program that calls foreign code, the device driver, says so.

A kernel compiler should be small enough to audit.

QuestionWhat cancho-gpu does
Can the compiler call into C or touch the network?No. Its report lists args, err_write, fs_read, fs_write, heap and io_write, and says it never touches the network or foreign code. tests/authority.sh fails the gate if that changes.
How do I know the output is right?The Rust emitter is the oracle: goldens are recorded from it, never from this compiler, and a live differential runs the same cases against a build of it. A CPU interpreter checks what a kernel computes, and a device program compares the GPU against it.
Does it run on a GPU?Metal: yes, on Apple Silicon, with the result inside the 2e-2 tolerance of the interpreter. CUDA: only against a mock driver so far, because no machine here has an NVIDIA GPU. The page and the README say which is which.
Is it an inference runtime?A first one. cancho-gpu-run and cancho-gpu-run35 run Qwen2.5-0.5B and Qwen3.8-27B: every layer is a compiled kernel on a Metal GPU. The 0.5B model gives the same greedy tokens as Hugging Face transformers; the 27B (NVFP4 weights from Ollama's store, 48 gated-delta layers) matches a reference implementation's golden log-probabilities to 1e-4 and decodes at about 24 tokens a second, against about 42 for Ollama in the same benchmark run. Serving is open.

Every claim has a measurement, or says it has none.

The oracle is external, so "it works" is a comparison, not an opinion. Where a claim turned out false, the design document was corrected in place.

159cases byte-identical with lex-gpu's Rust emitter: 133 emit, 26 refused by both
24interpreter runs with the same summary as the Rust's, f32 order included
~5,000hostile files and texts across the GGUF, safetensors and tokenizer readers: none traps or hangs; every refusal names its rule
0differences from the oracles on 5 real GGUF models, 3,379 Qwen3.8 tensors, and 3,811 records through 4 real tokenizers; the sampler's picks match on 60,000+ rows

The design document holds how it is built and what it cost; the device document what is and is not proved on a GPU; the runtime document where each reader differs from its oracle, and the kernels document the context limit.

Where it fits.

Use it for

  • Compiling .chx tile kernels to CUDA C and Metal with a small, auditable toolchain
  • Checking a kernel on the CPU before a GPU is involved
  • Trying a cancho program that drives a GPU through a thin C shim

Not yet

  • CUDA on real hardware, Hopper, AMD
  • Speed on the 27B model, long contexts (it needs a change to the language), serving
  • Attention over more than 1364 positions (it needs a change to the language)
  • Speed: reach and agreement are measured, timing is not

Try it.

You need the cancho compiler at the commit pinned in cancho.toml, and Rust to build it.

git clone https://github.com/alpibrusl/cancho
git clone https://github.com/alpibrusl/cancho-gpu && cd cancho-gpu
REV=$(sed -n 's/^cancho = "\([0-9a-f]*\)".*/\1/p' cancho.toml)
(cd ../cancho && git checkout "$REV" && cargo build --release -p cancho)
export CANCHO=$PWD/../cancho/target/release/cancho
$CANCHO build
mkdir -p out
build/cancho-gpu emit tests/chx/ported/gemm_fp4.chx out m=128 n=128 k=64

Other commands: cancho-gpu check <file.chx> [name=value ...] [--run] and cancho-gpu gguf <file.gguf> [--sum]. scripts/gate.sh is everything CI runs.

Status: alpha

  • Built: a model runner for Qwen2 on Metal, the parser, checker, CUDA and Metal emitters, the CPU interpreter, both device paths, exp/log/softmax, the GGUF and safetensors readers, a BPE tokenizer, a sampler, and rope, kv_append, attention and gate kernels.
  • Open: split-KV attention (#6), serving (#7), AMD (#9), model adapters (#10).
  • Unproven: CUDA on a real GPU; the kernels' speed against the best runtimes (about half of Ollama's on the 27B).
