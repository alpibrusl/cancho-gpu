GPU kernels that say what they can do.

Write a tile kernel once. The compiler checks it, refuses what is wrong and names the rule, and writes CUDA C and Metal. The same kernels run Qwen3.8‑27B on a Mac's GPU.

Try itSee the evidence

Refuses wrong programs

Every tile is consumed exactly once; bounds, shapes and the threadgroup budget are checked, and a refusal names the rule it broke.

One source, two targets

The same .chx kernel becomes CUDA C and Metal, recorded for 245 emitting cases and 27 refusals, each held byte for byte to the previous record (they first agreed with the Rust implementation this language began as).

Held to numbers

Every numeric kernel is checked against a float64 reference written from the mathematics, and nineteen are checked to fail when broken on purpose. The goldens are a regression record of this compiler. A CPU interpreter says what a kernel computes; on a Mac the GPU agrees with it to about 1e-6.

Runs a real model

Qwen3.8-27B decodes at 27.4 tokens a second on a Metal GPU (39.9 with speculative decoding), with the same tokens and top five as a reference's log-probabilities.

Trains and fine-tunes on the GPU

A network trained with Adam without its parameters leaving the GPU (the loss equals torch.optim.Adam's to six digits), then a GPT of up to 59.95 M parameters (167.8 ms a step against torch MPS's 196.7) and Qwen2.5 with LoRA (889.2 ms against 1,142.0 for float16 autocast), with loss curves equal to peft's. The CNN is 1.7 times slower than torch. The table.

Honest about what is missing

CUDA has run only against a mock driver, the 27B decodes at 88% of Ollama's speed with speculation (60% without), attention stops at 1024 positions in the runner, every training comparison is one run on one machine, and no tuned model for the cancho-code experiment exists yet. The list.

An authority you can read

The report lists exactly what the compiler may do, and the gate fails if it widens. The one program that calls foreign code says so.

What the promise does not establish: that a kernel is fast (speed is measured, against torch for training and against Ollama and MLX-LM for decoding: faster than torch on the GPT and the Qwen fine-tuning steps, slower on the CNN and below Ollama on the 27B), that CUDA works on a real GPU (it has run only against a mock driver), or that a kernel computes what you meant (the checker proves linearity, bounds and shapes, not intent). The stories below say what each run shows and what it does not.

Five things that were actually run.

Each story is a real command and what it printed, with the document that holds the run and a line on what it does not show.

A wrong kernel is refused, and the rule has a name

A kernel that loads a second tensor and never uses it. The checker refuses it and says which tensor and which rule; nothing is written.

$ cancho-gpu check leak.chx n=8
error[leak]: `w.1` is never consumed; drop it, yield it or move it into an op

Shows: the refusal and its stable rule tag (every rule has a fixture, rules.md). Does not show: that a kernel which passes computes what you meant.

Run a kernel on your own numbers

The backward of a matrix product, on two small matrices you can check by hand: dy is 1 2 / 3 4 and w is 1 0 2 / 0 1 3, so dx = dy w is 1 2 8 / 3 4 18.

$ cancho-gpu run tests/chx/bwd_dx.chx r=2 n=2 k=3 --target nvidia-ada \
    --in dy dy --in w w --out dx
1.0 2.0 8.0 3.0 4.0 18.0

Shows: the CPU interpreter, with inputs from files and the whole output printed (run.md). Does not show: a GPU run; the device programs do not take input yet.

Train a small model with kernels as the objective

A least-squares fit whose loss and gradient are computed by cancho-gpu kernels, driven by cancho-opt's BFGS: 12 evaluations to within 1.1e-5 of the normal-equations solution, at 28 to 36 ms an evaluation.

$ opt minimize --method bfgs --x0 0,0,0 -- python3 examples/train/lsq_objective.py ...
{"method":"bfgs","x":[1.5065,-2.0052,0.4572],"nfev":12,"converged":true, ...}

Shows: a kernel as an optimiser's objective, on the CPU interpreter (examples, training.md). Does not show: more than 32 parameters or any speed claim; this is the CPU path, and training on the GPU is done in sessions (resident.md).

A 27B model on the same kernels

Qwen3.8-27B (NVFP4, read from Ollama's store) generating on a Metal GPU: 27.4 tokens a second, 39.9 with speculative decoding, against 45.3 for Ollama in the same invocation, on one Apple M4 Max.

$ cancho-gpu-run35 <ollama store> tests/chx "<prompt>" 64

Shows: it runs and agrees with a reference's log-probabilities to 1e-4 (benchmark.md). Does not show: that it is the fast way to run this model; it is not.

Compared with OpenNN

A two-layer sigmoid network, forward only, the same weights in both: outputs agree to 1.4e-7 of a binary64 reference. OpenNN's call takes about 2.5 microseconds in process; cancho-gpu's CPU interpreter takes milliseconds as two processes. No ratio is claimed: they measure different things.

$ python3 bench/opennn/compare.py --opennn build/forward_opennn --gpu build/cancho-gpu

Shows: agreement and the two timings, with the differences and where cancho-gpu is worse (comparison.md). Does not show: any GPU, training, or a larger network (the one training comparison, against OpenNN's CPU path only, is in resident.md sections 13 and 14).

How it works.

A kernel is checked before it is lowered; a refusal never reaches a GPU. The interpreter is the reference for what a kernel computes.

Look at one kernel.

The real source of swiglu.chx, what the compiler writes for each target, and what it says to a program that breaks a rule.

// a = silu(g) * u over a row of n: the gated activation of a SwiGLU MLP.
algo swiglu(n)
  in  g: f32[1, n]
  in  u: f32[1, n]
  out y: f32[1, n]
{
  let gt = load g
  let ut = load u
  let sg = sigmoid &gt
  let a  = gt * sg
  store a * ut -> y
}

schedule swiglu for apple-m-series { threads 256 }
schedule swiglu for nvidia-ada     { threads 256 }
kernel void swiglu_17408(
    device const float* p0_g [[buffer(0)]],
    device const float* p1_u [[buffer(1)]],
    device float* p2_y [[buffer(2)]],
    uint tid [[thread_index_in_threadgroup]],
    uint3 tgpos [[threadgroup_position_in_grid]])
{
    const uint gid = tgpos.x;
    float v2[68];
    for (uint k = 0; k < 68u; ++k) {
        const uint e = k * 256u + tid;
        if (e < 17408u) {
            v2[k] = float(1.0f / (1.0f + precise::exp(-float(float(p0_g[(uint)(0) * 17408u + (uint)(0) * 1u + ((e))])))));
        }
    }
    float v3[68];
    for (uint k = 0; k < 68u; ++k) {
        const uint e = k * 256u + tid;
        if (e < 17408u) {
            v3[k] = float(float(float(p0_g[(uint)(0) * 17408u + (uint)(0) * 1u + ((e))])) * float(v2[k]));
        }
    }
    float v4[68];
    for (uint k = 0; k < 68u; ++k) {
        const uint e = k * 256u + tid;
        if (e < 17408u) {
            v4[k] = float(float(v3[k]) * float(float(p1_u[(uint)(0) * 17408u + (uint)(0) * 1u + ((e / 1u))])));
        }
    }
    for (uint k = 0; k < 68u; ++k) {
        const uint e = k * 256u + tid;
        if (e < 17408u) {
            p2_y[(uint)(0) * 17408u + (uint)(0) * 1u + (e)] = float(float(v4[k]));
        }
    }
}

A kernel compiler should be small enough to audit.

QuestionWhat cancho-gpu does
Can the compiler call into C or touch the network?No. Its report lists args, err_write, fs_read, fs_write, heap and io_write, and says it never touches the network or foreign code. tests/authority.sh fails the gate if that changes.
How do I know the output is right?Numbers: every numeric kernel is held to a float64 reference written from the mathematics, and a device program compares the GPU against the CPU interpreter. Text: the CUDA and Metal output is recorded in goldens, which are a regression record of this compiler, not an answer. They first agreed byte for byte with a Rust implementation of the language, which was the oracle until it was retired; for CUDA, which no machine here can run, that was the only independent check, and nothing replaces it yet.
Does it run on a GPU?Metal: yes, on Apple Silicon, with the result inside the 2e-2 tolerance of the interpreter. CUDA: only against a mock driver so far, because no machine here has an NVIDIA GPU. The page and the README say which is which.
Is it an inference runtime?A first one (and a training stack, below). cancho-gpu-run and cancho-gpu-run35 run Qwen2.5-0.5B and Qwen3.8-27B: every layer is a compiled kernel on a Metal GPU. The 0.5B model gives the same greedy tokens as Hugging Face transformers; the 27B (NVFP4 weights from Ollama's store, 48 gated-delta layers) matches a reference implementation's golden log-probabilities to 1e-4 and decodes at 27.4 tokens a second (39.9 with speculative decoding), against 45.3 for Ollama in the same benchmark run. It also serves an OpenAI-compatible chat endpoint with streaming (one request at a time).

A real session, replayed.

Run a kernel on your own numbers.

cancho-gpu run executes a kernel on the CPU interpreter over inputs you give it and prints the whole output. It exists so a kernel can be the objective of an optimiser, and a small model has been trained that way. The command does not run on a GPU; training on the GPU is done in sessions (below).

$ printf '1 2\n3 4\n' > dy; printf '1 0 2\n0 1 3\n' > w
$ cancho-gpu run tests/chx/bwd_dx.chx r=2 n=2 k=3 --target nvidia-ada \
    --in dy dy --in w w --out dx
1.0 2.0 8.0 3.0 4.0 18.0

Backward kernels

dx, dw, db and the sigmoid's, held, element by element, to a reference that is itself checked against finite differences.

A fit, with kernels as the objective

A least-squares fit driven by cancho-opt's BFGS, loss and gradient computed by these kernels: 12 evaluations, within 1.1e-5 of the normal-equations solution, 28 to 36 ms an evaluation on the CPU interpreter.

What it cannot do

At most 32 parameters through opt, and the CPU interpreter only. Whether a GPU helps at that size: with text on a pipe it cannot (training.md); the sessions, with the data on the device, are the GPU path.

Design, gates and numbers: the run document and the training document, which also says why training does not belong in the compiler yet. Examples: cancho-gpu and cancho-opt.

Where it fits.

Use it for

  • Compiling .chx tile kernels to CUDA C and Metal with a small, auditable toolchain
  • Checking a kernel on the CPU before a GPU is involved
  • Trying a cancho program that drives a GPU through a thin C shim
  • Training and fine-tuning small models on a Mac's GPU, checked against a float64 specification and torch (one machine, one run each)

Not yet

  • CUDA on real hardware, Hopper, AMD
  • Decoding as fast as Ollama on the 27B (88% with speculation), long contexts (it needs a change to the language), concurrent requests
  • Attention over more than 1364 positions (it needs a change to the language)
  • Training contexts above 128 (GPT) or 512 (Qwen), a CNN as fast as torch, 90% on CIFAR-10, a 7B model (the 4-bit base is built for the 1.5B; the 7B is in progress)
  • Results of the cancho-code fine-tuning experiment: the design and the untuned baselines exist, no tuned model does

Status: alpha

  • Built: a model runner for Qwen2 on Metal, the parser, checker, CUDA and Metal emitters, the CPU interpreter, both device paths, exp/log/softmax, the GGUF and safetensors readers, a BPE tokenizer, a sampler, rope, kv_append, attention and gate kernels, backward kernels, run (a kernel on your inputs, CPU interpreter), and training sessions on Metal: a GPT (trained and served), a CNN, Qwen2.5 LoRA and full fine-tuning, a ResNet-18-class backbone (equal to torch, not timed).
  • Since then: batched decode and an on-device sampler, a complete optimiser, text-to-image on Qwen-Image-2.1-Turbo (1024 × 1024), and the weight-space editing pipeline (see below). Image editing runs end to end on one photograph (slower than torch); video is not started.
  • Open: split-KV attention (#6), concurrent serving and a prefix cache (#7), AMD (#9), model adapters (#10), run on a GPU through the device programs, the cancho-code fine-tuning experiment's tuned arms (M8), the vision backbone's timing (M9 V2), and the 7B model for the 4-bit base (QLoRA is built for the 1.5B, section 27; the 7B is in progress).
  • Unproven: CUDA on a real GPU (so every training number is Metal); any result on a second machine or a second seed; the 27B's decode speed against Ollama's (88% with speculation, 60% without).

Decode speed, tokens a second, greedy, 128 tokens of a prose continuation, five runs each, one machine (Apple M4 Max, 64 GB), one invocation, with a light background load (load average about 2 at the start; the runs themselves varied by under 2%) (docs/benchmark.md). Ollama decodes this model with speculative decoding from the model's own draft head; cancho-gpu does too in the speculative row (a chain of two drafts, three rows checked a pass, the same tokens as plain decoding: #26), and is not there yet. MLX-LM uses a different 4-bit quantisation. Prompt processing takes eight tokens at a time: a 49-token prompt in 0.65 s, against 2.2 s a token at a time (one run each).

Correct, not just fast

Three prompts, eight steps each: the same token and top five as the reference's golden log-probabilities, logit gaps within 1e-4.

Small first

Qwen2.5-0.5B gives the same greedy tokens as Hugging Face transformers in float32, every top-5 logit within 1e-4, at about 6 ms a token.

Measured, with the misses

An experiment that looked like a win and was a bug, and one that did not move the pipeline at all, are in #24 and #26.

Not only run: trained, on the same kernels.

Training happens in sessions: compile and upload once, then run many steps for one request, with the parameters, the optimiser's state and the data staying on the GPU. Every model below is held to a float64 specification written for it and to torch or peft. All of it is Metal, on one Apple M4 Max, one run and one seed each (resident.md).

A GPT, trained and served

3.26 M to 59.95 M parameters, on characters and on a 2,048-token byte-pair vocabulary built here (sections 15 to 17, 19). The 59.95 M model takes 167.8 ms a step against torch MPS's 196.7, with validation curves within 0.013 nats. Served from a forward-only session, all 576 greedy tokens equal torch's, at 650 tokens a second against torch's 340.

A CNN on real CIFAR-10

A 0.85 M-parameter ResNet reaches 87.4% test accuracy, torch's 87.0%, with no augmentation (section 18). The roadmap's 90% is not met by any runtime, and a step takes 17.6 ms against torch MPS's 10.6: 1.7 times slower.

Qwen2.5, fine-tuned

The forward pass equals transformers' (loss within 1.2e-4 on the 0.5B, 5.2e-6 on the 1.5B); LoRA gradients at cosine 0.99986 and 0.99938 or better against peft; a 300-step run (0.5B) and a 150-step run (1.5B) whose loss curves equal peft float32's; full fine-tuning of the 0.5B with the embedding table trained, equal to torch float32 (sections 20 to 24). A 4-bit NVFP4 base for the 1.5B's LoRA (section 27): the loss 8.6e-5 from transformers', gradients at cosine 0.997738 or better, the adapters winning back 45.6% of the 4-bit base's 0.0492-nat cost, at 2,483.1 ms a step against 2,480.6 on an f16 base and 17.52 GB against 19.29.

Speed and memory against torch

0.5B LoRA step: 889.2 ms and 16.14 GB against float16 autocast's 1,142.0 ms and 27.48 GB. 1.5B: 2,467.3 ms and 19.38 GB against 2,743.8 ms and 39.93 GB. Full fine-tuning of the 0.5B: 1,381.4 ms and 21.03 GB against 1,450.8 ms and 44.56 GB (torch float32). The memory clause of the 0.5B LoRA exit was not met: 59% of torch's, not under half.

A vision backbone for a robot

A ResNet-18-class network (11,181,632 parameters, 96 × 128 input) trained in a session, its loss and gradients equal to torch's: loss 2.78119 against torch float32's 2.78022 on Metal (section 26). Not timed: no step time is claimed, and no robot data exist yet.

An experiment with no result yet

Does fine-tuning a small model on cancho make it better at cancho-code's job? The design is fixed before any result, the data (6,946 records, 2.78 M tokens, with a contamination check) is built, and the two untuned baselines are near zero: 0.012 of the oracle's points for the better arm. No tuned model has been trained, and no training result is in (roadmap-models.md section 7). The 7B model that the 4-bit work (QLoRA) was designed for has not been run and is in progress.

Beyond training: sampling, images, edits.

What was added since the training sections above. Same rules: Metal on one Apple M4 Max, each piece held to a float64 or torch reference written for it, and each ends in what it does not show.

A batched decode and a sampler on the device

Up to 32 sequences of Qwen2.5-1.5B a step, with the sampled ids staying on the GPU: the same 48 tokens as transformers' greedy generation on two chat prompts, 35.6 ms a step at 32 sequences with 1,152-position caches (43.0 ms with LoRA adapters). Temperature sampling by inverse CDF takes 0.99 ms for 32 rows over a 152,064-token vocabulary; detokenisation matches Hugging Face's on 461 of 461 (decode.md, sampler.md). Written for cancho-rl, which uses it for reinforcement learning on this GPU.

An optimiser that is complete

Global-norm gradient clipping, decay groups, a learning-rate schedule and gradient accumulation, written as .chx kernels and held to torch.optim.AdamW, clip_grad_norm_ and the schedulers, with a binary64 numpy version where torch is float32; the CNN, ResNet and Qwen LoRA sessions take opt= (optimizer.md).

Images: Qwen-Image-2.1-Turbo

A 7.12 B-parameter diffusion transformer, its text encoder (the Qwen3-VL language model) and its VAE decoder, from a prompt and a seed to pixels, as kernels. It is closer to the exact float64 pipeline than torch's own BF16 is: the 1024 × 1024 image is 0.16 of 255 from float64 (49.3 dB), torch's is 4.75 (26.2 dB). On time, a 1024 × 1024 step takes 6.25 s against torch MPS's 4.99 s; the whole pipeline is about 52 s against 41 s (an estimate from the measured stages), after the attention was moved to the matrix unit. Image editing works too, through the vision tower, the language model reading the photograph, a VAE encoder and the transformer with the photograph as a cached prefix: one real public-domain photograph, one prompt, comes out as the same edit as torch's (final latents 1.0% of their rms apart, 39.1 dB between the images) in 150 s against torch's 54 s, so torch is faster here. Video is not started (diffusion.md).

Weight-space editing, with the negative results

A pipeline with pre-registered gates for a published edit of a model's weights: the edit costs 0.0205 nats a token and +1.3% perplexity, which fails the registered 0.02 gate by its interval's upper bound; a gradient search for the edit that fixes loops was not recovered, and a rank-1 edit built from gradients broke held-out loops. On the engine side, a greedy runner and the edit as a 262,844-byte patch run on Metal in f32 and f16, and teacher-forced agreement with a float64 reference holds to 16,510 positions (weight-space-w4.md, weight-space-w4-r4.md, weight-space.md).

The training session writer, in cancho

The session file of a Qwen2 LoRA run (qsw) is now written by a cancho program, byte for byte what the Python writer wrote; it also writes the gradient-only, forward-only and prefill sessions the above need.

Reading it. For the GPT and for Qwen2.5 fine-tuning cancho-gpu takes less time a step than torch on MPS (1.28 times faster than float16 autocast on the 0.5B LoRA step, 1.11 times on the 1.5B's, 1.05 times on the 0.5B's full fine-tuning), with loss curves equal to the digits in the sections, and uses less memory in the three fine-tuning rows that have a torch number; the 0.5B forward pass uses more. It is slower on the CNN, and its decoding is slower than Ollama's on the 27B (88% of it with speculation) and than MLX-LM's on the 0.5B model. This is not a claim about torch tuned (compiled, with graphs), another machine or NVIDIA, and the fine-tuning rows are on this repository's own Markdown, Rust and cancho files: a measure of agreement with torch, not of how good a tuned model is.

Against OpenNN. comparison.md is the forward pass of one small two-layer sigmoid network on a CPU: both agree with a binary64 reference to 1.4e-7, and no timing ratio is claimed because the two measure different things. It has no GPU in it and no training. The only training comparison with OpenNN (resident.md sections 13 and 14, the third row above) is against OpenNN's CPU path, which was built without BLAS and so is not its best. No comparison against OpenNN's GPU path exists, for the forward pass or for training.

Known gaps.

Assembled from the limits paragraphs of the sections cited. None of them is hidden by the table above.

Hardware and method

  • CUDA has run on one NVIDIA L4 only (it compiles and 176 of 188 cases agree with the interpreter), otherwise a mock driver; no Hopper, no AMD. All training numbers are Metal on one Apple M4 Max.
  • One run, one seed for every comparison with torch; a 0.01-nat difference between GPT runtimes is inside what another seed would move (resident.md 19.1).
  • The Qwen held-out set is 7 files and 16,384 tokens; the 1.5B run is 150 steps; full fine-tuning is 40 and 300 steps at one untuned learning rate. Some step times were measured with another process on the machine, and the sections say which.

Where it misses

  • M4's 90% is unmet: 87.4% on real CIFAR-10 with no augmentation; torch gets 87.0% (18.1).
  • The CNN is slower than torch (17.6 ms against 10.6): 186 launches a step, and the ResNet-18-class network has 287; the one fusion the surface allows would remove about 14% of them (estimate; 18.2, 26.3, roadmap 8.4).
  • M7.3's memory clause is unmet for the 0.5B: 59% of torch float16 autocast's footprint, not under half. Met narrowly for the 1.5B (48.5% by footprint, 51.3% by torch's driver number) after two memory changes (22.3, 23.5).
  • Decoding is slower than Ollama on the 27B and than MLX-LM on the 0.5B model.

Costs and ceilings

  • The vocabulary is a one-hot product, since the surface has no gather or atomics: +14% of a GPT step at 2,048 tokens, about 203 ms of a 1,380 ms Qwen step (15%) at 151,936. A GPT vocabulary above about 2,048 is not built (17, 24.5).
  • Contexts: the GPT trains at 128, Qwen at 512; the decode runners stop at 1,024 positions (256 for the 0.5B runner); split-KV is not built.
  • Precision: a static loss scale of 16 (above 64 it is silently wrong); f16 gradients make Adam move near-zero rows by noise, 11.3% off peft in layer 0's q B after 300 steps, with the held-out loss equal to 6e-5; whether an f32 gradient would remove it was not tried (22.4).

Not done

  • 1.5B full fine-tuning is four steps: it fits (44.27 GB of 64), with no held-out loss and no torch comparison (24.9).
  • The 7B is not run. The 4-bit base (QLoRA) is built and measured on the 1.5B only: one seed, 150 steps, group size 16 only on the GPU, 54.4% of its loss cost remaining; no torch comparison (27.4 to 27.6).
  • M8 has no training result; the untuned baselines are near zero (A: 0.012, B: 0.000; Claude Haiku 5.5: 0.99) and the tuned arms will be read on compile rate and refusal tags.
  • M9: the backbone is not timed; no robot or synthetic data, no regression head (26.4, roadmap 8.3).
  • A text resident file is capped at 16 MiB (binary is not); a table must fit the 512 MiB byte pool, so a 300-step Qwen run is five or six sessions.

Measured, not promised.

"It works" is a comparison with an independent reference, not an opinion; the CUDA text, which no machine here can run, is the exception. Who ran what: the case counts and the interpreter runs are checked by CI on every push (scripts/gate.sh); the 27B and Metal numbers were made by hand on one Apple M4 Max and are reported in benchmark.md, the training and fine-tuning numbers (one run each) in resident.md; the OpenNN numbers are one run on a 4-vCPU container, in comparison.md. Where a claim turned out false, the design document was corrected in place.

272cases held to recorded goldens (245 emit, 27 refused); 218 of the first ones agreed byte for byte with the Rust implementation, now retired as the oracle
65interpreter runs recorded as goldens; 51 of them had the same summary as the Rust's when it was the oracle, f32 order included
4,987hostile files and texts across the GGUF, safetensors and tokenizer readers: none traps or hangs; every refusal names its rule
0differences from the independent readers on 6 real GGUF models and 3,379 Qwen3.8 tensors; the sampler's picks match on 2,269 rows. the tokenizer agrees with Hugging Face on 5,300+ records of real and random text across two real Qwen tokenizers (it did not, until issue #51 was fixed)

The design document holds how it is built and what it cost; the device document what is and is not proved on a GPU; the runtime document where each reader differs from its oracle, and the kernels document the context limit.

Try it.

You need the cancho compiler at the commit pinned in cancho.toml, and Rust to build it.

git clone https://github.com/alpibrusl/cancho
git clone https://github.com/alpibrusl/cancho-gpu && cd cancho-gpu
REV=$(sed -n 's/^cancho = "\([0-9a-f]*\)".*/\1/p' cancho.toml)
(cd ../cancho && git checkout "$REV" && cargo build --release -p cancho)
export CANCHO=$PWD/../cancho/target/release/cancho
$CANCHO build
mkdir -p out
build/cancho-gpu emit tests/chx/softmax.chx out r=16 n=256

Other commands: cancho-gpu check <file.chx> [name=value ...] [--run], cancho-gpu run <file.chx> [--in NAME FILE ...] [--out NAME ...] and cancho-gpu gguf <file.gguf> [--sum]. scripts/gate.sh is everything CI runs.
