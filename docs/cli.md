# cancho-media: one command line for images and video

`scripts/media` (the program is `tools/media.py`, Python standard library, run with the venv of the first image edits) wraps the generators that exist; it does no GPU work of its own and adds no kernel.

```
scripts/media doctor
scripts/media models
scripts/media video "A red fox running through fresh snow in a pine forest at sunrise, cinematic" -o out/fox --frames 17 --size 640x352 --seed 1
scripts/media video "a fox running in the snow" -o out/fox --rewrite
scripts/media rewrite edit "make it look nicer" --image photo.jpg
scripts/media edit photo.jpg "Make it a bright sunny afternoon." -o out/sunny --weights DIR --text-weights DIR
scripts/media image "A lighthouse on a rocky coast at dusk, photograph" -o out/lighthouse --size 1024x1024 --seed 2
```

* **`video`**: `tests/wan_text_gpu.py` (umT5's encoder as a Metal session since 2026-11-23, `docs/diffusion.md` V3; its f16 weights, 9.3 GB, are written to `<cache>/umt5-f16` on first use; it was `tools/wan_text.py`, torch on the host) then `tests/wan_video_gpu.py` (FastWan2.2-TI2V-5B, three DMD steps, the VAE decoder, Metal). Writes `video.gif`, `video.mp4` (if `ffmpeg` exists), `frames/`, `prompt.txt` in `-o DIR`. `--frames` is rounded up to 1 + 4k; `--size WxH` in pixels, multiples of 32. The 10 GB of f16 weight files are written once to `~/.cache/cancho-media/wan-f16` (`CANCHO_MEDIA_CACHE`, `--wdir`) and reused.
* **`video --image --segments N [--then PROMPT]... [--no-correct]`** (docs/video-chain.md; 2026-11-17): chains N clips, each `--frames` long, each starting from the **last frame** of the previous one, with the **ramped colour correction** (each clip's frames are moved toward the first picture's colours, 0 on its first frame to fully matched on its last, which is the one carried on). `--then` gives the next clip's prompt (repeat; the default is the first prompt again); seeds are `--seed`, `--seed + 1`, ... The joined video has `frames + (N - 1)(frames - 1)` frames in `-o DIR` (`frames/`, `video.gif`, `video.mp4`, `prompt.txt` with one prompt a line); each clip is in `DIR/segK/`, its corrected frames in `corrected/`. **Refused, exit 2:** `--segments`, `--then` or `--no-correct` without `--image`, `--segments` below 1, **above 2 without `--force`** (the third clip of the measured chain smeared), more `--then` than clips after the first. **Measured once (2026-11-17, the fox picture, 2 x 17 frames):** 33 frames in 3 min 1 s; the first clip matches the earlier scratch chain (0.4 of 255 at frame 16), the fox runs on in the second. The correction is on by default; `--no-correct` lets the colours drift (red 127 to 99 and saturation 18 to 33 over three clips in the measured chain). **One picture, one prompt, one seed; not looked at beyond that run.** Each clip leaves its 1.3 GB or more of work files in `DIR/segK/work` (a full disk made a run fail late: `errno 28` in the decoder).
* **`--rewrite` (video, edit) and `media rewrite`** (docs/studio-rewrite.md; the studio's layer, from the command line, 2026-11-17): before the GPU job, the local model (`--rewrite-model`, default `qwen3.8:27b-mlx`, Ollama at `127.0.0.1:11434` and nowhere else) rewrites the prompt with the system prompts in `studio/rewrite/` (`video.txt`; `edit.txt`, and the model sees the picture). Both prompts are printed (stderr), `prompt.txt` holds the one used and **`prompt.orig.txt` the original** when they differ. It runs inside the GPU lock, so the 16 GB model (unloaded when it answers) never shares memory with a job. **It fails open as the studio does** (Ollama down, a wrong model name, an unusable answer: the original is used and the reason printed). **Refused, exit 2:** `--rewrite` with `--image` on `video` (no template; not measured), with more than one `--also` on `edit`, and when `build/rewrite_cli` is missing (the `cancho build` line is in the message); `image` has no `--rewrite` (no template). **With one `--also` the rewriter reads both pictures** (Ollama's `images` list, in order: image1, image2) and uses `studio/rewrite/edit2.txt`, which names them `image1` and `image2`; `rewrite_cli ask` takes the second picture as a last argument. `media rewrite video|edit PROMPT [--image P [--also P2]]` prints only the rewritten prompt (exit 1 if it fell back to the original) and needs no GPU. **Measured once (2026-11-17):** 6 s for a video prompt; a 9-frame FastWan run with `--rewrite` ended with `prompt.orig.txt` and the new `prompt.txt`; a wrong model name ran the job with the original; `/api/ps` was empty after. **Two pictures (2026-11-17): `studio/rewrite_check.sh` 0 failures** (the request carries `"images":[A,B]` in order, one picture carries one, an unreadable or first-less second picture is refused, and the mutant that drops the second picture is killed), and the real model wrote an instruction naming image1 and image2 for two pictures. **Not run: a real `edit --also --rewrite` through the GPU**, and the rewritten two-picture instruction was not compared with the original. **Whether a rewritten prompt gives a better video is not measured here**: docs/studio-rewrite.md section 8 is the test and it has not been run.
* **`video --precise`** (`docs/diffusion.md` section 6, V3c; 2026-11-24): the transformer's products take their activations in f32, not f16. The final latents are then 0.9% of their rms from the ones float64 arithmetic gives for the same rows, seed and noise, and the frames 50 to 55 dB from those latents' frames; without it 44% and 17 to 20 dB (a valid sample of the model, not this seed's video: the model multiplies a rounding several hundred times, V3b). It costs 2 to 3 s (20.3 to 23.8 s against 17.9 to 18.4). Refused with `--image` (the base model's steps were not measured). Metal only.
* **`video --image PICTURE`** (docs/video-image.md): the picture is the first frame; the base model (Wan2.2-TI2V-5B, `--model wan2.2-ti2v-5b-base`, chosen by `--image`) runs 30 Euler steps with guidance (`--steps`, `--guidance`) and continues it (guidance 3.5 and Wan's own negative prompt by default, measured in docs/video-image.md section 7: the model's 5 made the clip fall apart after about frame 8). The picture is covered and cropped at the centre to `--size`; its latent is made by `build/wan_vae_enc_gpu` (build line in the refusal). The base model's f16 files (10 GB) are written to `~/.cache/cancho-media/wan-f16-base`. **Measured once (93 s for 17 frames of 640 x 352): the scene continues, the action in the prompt barely, and streaks of colour appear** (the base model's behaviour at this size).
* **`edit`**: `tests/edit_pipeline_gpu.py --resident` (Qwen-Image-2.1-Turbo: vision tower, language model, VAE encoder, eight steps, decoder). Writes `edited.png`.
* **`--model NAME`** on `video`, `edit` and `image`; **`models`** lists them. The registry (`MODELS` in `tools/media.py`) holds, per task, the model's name and Hugging Face repositories; today `video`: `fastwan2.2-ti2v-5b` (default), `edit`: `qwen-image-2.1-turbo` (default), `image`: none. Any other name is refused with the supported list (run: `wan2.1`, `flux`, `foo`). Adding a model is a registry entry **and a driver for it**: the drivers fix the architecture's dimensions, kernels and sampler, so `--model` does not make another checkpoint run by itself.
* **`doctor`**: what is installed (platform, session binary, the two Wan and the Qwen snapshots, ffmpeg, the python modules, free disk).
* **Offline by default.** `media` sets `HF_HUB_OFFLINE=1` for every stage, so `transformers` and `huggingface_hub` read the local cache and do not ask the Hub whether a newer revision exists (they otherwise do, on every call, sending the repository and file names, never the prompt or the image). `--online` (before the subcommand: `media --online doctor`) lifts it, for filling the cache the first time. A file missing from the cache is an error, not a download. Measured 2026-11-16 with the cache full: `video` (17 frames, 640 x 352; 18 s GPU stage, 27 s in all) and `edit` (90 s) both ran offline to the end. Not measured: network traffic itself (no capture); the claim is the library's documented behaviour plus both runs succeeding with the Hub switched off.
* **One GPU job at a time**: a lock file (`gpu.lock` in the cache directory) refuses a second run.
* **Limits** are the measured ones, not the model's; `--force` goes past them: more than 4,000 tokens (the denoiser's attention is the three-kernel one here, measured only to 1,100 tokens: the fused `ATT=1` of docs/diffusion.md V1b is **not** wired into `tests/wan_video_gpu.py`), more than 17 x 1024 x 576 pixel-frames of decode: the decoder runs out of GPU memory above about that (17 frames of 1024 x 576 and 33 of 640 x 352 run; 17 of 1152 x 640 and 33 of 960 x 512 do not: V2b).

## What was run (2026-11-15, Apple M4 Max, 64 GB)

* `doctor`: all rows `ok`.
* **`video`, 17 frames, 640 x 352, seed 1**, the fox prompt above: **44 s of wall clock** for the command (text encoder 12 s; the GPU stage 32 s: writing the weight files 13 s, three steps 3.3 + 1.1 + 1.1 s, decoder 12.2 s), `video.mp4` and `video.gif` written. One run, a cold start of the weight files; the result was looked at, not compared with torch's pipeline.
* Refusals checked by hand: a size that is not a multiple of 32, 121 frames at 1280 x 704 (27,280 tokens: refused for the tokens first), a missing image, missing edit weights, a second job while the lock is held, `image` with an empty prompt or a bad size.

## What this does not do

* **`edit` was not run end to end here.** The Qwen-Image-2.1-Turbo snapshot is in the cache, but the transformer's head-permuted f16 block weights (14 GB, `tests/dit_big.py`, docs/diffusion.md D7) are not on disk, and `media` does not make them: it refuses with the path it looked at. Its argument handling and refusals were run; the command it issues is the one `tests/edit_pipeline_gpu.py` documents.
* **`image` (text to image from a free prompt) runs** (2026-11-16, `tests/t2i_pipeline_gpu.py`, docs/text-to-image.md): Qwen-Image-2.1-Turbo, 8 steps, `--size WxH` (multiples of 32, at most 1024 x 1024; default 1024 x 1024), `--seed`, `--steps`, the edit's two weight directories; writes `image.png` and `prompt.txt` in `-o DIR`. **Measured:** 512 x 512 in 27 s for the command (about 25 s of GPU), 1024 x 1024 about 75 s of GPU (since 2026-11-23, the prefix pass on the text's own rows: 22.7 s and 61 to 63 s for the command, the same pixels, docs/text-to-image.md section 8); against torch's BF16 pipeline 39.6 dB at 512 and 26.9 dB at 1024 (the distance docs/diffusion.md D7 documented; the GPU is the nearer to the exact image). Refusals: an empty prompt, a size that is not a multiple of 32 or is over 1024 x 1024, missing weights.
* Image-to-video is `video --image` (above), not in the studio; no video editing, no audio; the text encoder of `video` is a GPU session (it was torch on the host until 2026-11-23), its tokeniser the `tokenizers` library; large videos wait on the decoder's time chunking and the fused attention's wiring.
