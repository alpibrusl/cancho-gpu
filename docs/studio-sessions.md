> **Status: slices 1 and 2 (section 8), 6 the gallery (section 9), and 3 the sessions page with the two-place menu (section 11) are built and checked; the library upload (10.3) and the picker (10.4) are built (section 12); 5, naming and deleting sessions, is designed, not built.** Claims say what was read in this repository (`studio/upload.cho`, `studio/results.cho`, `studio/jobs.cho`, `docs/studio-variations.md` section 3, `docs/studio-cases.md`) and what was not run. It completes `docs/studio-variations.md` V2 ("a result as the next input"), which was designed there and never built.

## 1. What is asked

"Several rounds of editing; see the original and the edited pictures; recover the prompts used in a job; a **refine** task where the user **selects which pictures to include**; a *session of edition*."

## 2. What exists today (read, not guessed)

* A job is `<id>.argv`, `<id>.log`, `<id>.state` and `out/<id>/`. The prompt, seed, steps and model are in `<id>.argv`; `job_page` already prints the prompt ("Prompt as written", and the rewritten one) and the parameters (`param_rows`). *Correction (2026-11-19, found when building slice 1): the first version of this document said the job page did not show the prompt in full. It does.*
* `POST /edit` keeps the person's pictures as `upload-N.*` and `upload-N-2.*` and the job page shows them beside the result (#224). Nothing says that job 12 was made *from the result of* job 9: every job is an island, and a second round means downloading the result and uploading it again.
* A job takes **at most two input pictures** (`image` and `also`); a third pushes the attention rows over what the kernels index (the refusal in `media`: 3 pictures at 1,048,576 pixels is about 12,416 rows against about 11,500). That limit bounds "select the images to include": **one or two**, not any number.

## 3. The model: a session is a tree of jobs, with no new kind of object

No session record is needed. Two small files per job, written by the server (the only writer of `*.argv`, as today), after the job exists:

* `<id>.from`: one line per input picture, `JOB NAME` for a result of an earlier job (`9 edited.png`) or `upload` for a file the person sent with this job. At most two lines.
* `<id>.root`: the id of the first job of the session. A job made from nothing earlier is its own root; a job made from job M has M's root.

A **session is the set of jobs with one root**. Rounds are the jobs ordered by id; the *tree* is whatever `.from` says (a refine of round 2 made after round 3 is a branch, and is shown as one). Nothing is copied: a refine job's input is `out/M/edited.png`, **named by the server from a job id** and checked (done, an edit, the file exists), never a path from the client (`docs/studio-variations.md` section 3).

*Why not copy the picture into `upload-N.*`?* A copy would keep the job whole if `out/M` is deleted, at the price of a second 1-2 MB file per round. Chosen: **link, no copy**, because `out/` is never deleted by the studio; a job whose source is gone shows "source removed" and its refine is refused. Reversible if the data directory is ever pruned.

## 4. Pages and routes

| route | what | built from |
|---|---|---|
| `GET /sessions` | one row per root: thumbnail of the first picture and of the latest result, round count, state of the last round, newest first | the `.root` files |
| `GET /sessions/ROOT` | **the session page**: a row per round, in order: *input pictures* -> *result*, the prompt, seed, steps, model, state, a link to the job; a branch is indented under the round it came from. At the bottom the **refine form** | `.from`, `.root`, `argv`, `prompt.txt` |
| `GET /edit?from=JOB` | the edit form with the prompt, seed, steps and model **prefilled** from that job ("use this prompt again"), and that job's result as the picture | `argv` |
| `POST /edit` | gains `from_job` (+ `from_name`) and `from_job2`: pictures chosen from earlier results instead of (or with) an upload | `upload.cho` |

The job page (`/jobs/N`) gains: "Refine this result" (to the session page, this result preselected) and "Use this prompt again" (`/edit?from=N`); and a link to its session. `/jobs` rows link to the session.

### The refine form (the "select the images" part)

Under the session's last round: every picture of the session as a **thumbnail with a checkbox** (the originals first, then each round's result), at most two checked; a third checkbox is disabled by a line of JavaScript and refused by the server regardless (422, the limit above). Plus an optional upload of a new picture (it counts as one of the two), the instruction box with the cases' tips, and Start. Without JavaScript the form still works: the server refuses more than two with a one-line reason. Same style as the other pages (`docs/studio-design.md`): a server-written page, no cancho-ui island, because a file picker with thumbnails is exactly what the island cannot do (`docs/studio.md`, "Editing a picture chosen in the browser").

## 5. Refusals (each with a tag in the answer, none queues anything)

`from_job` not digits (422); not an edit or not done or no result file (422); more than two pictures in all (422); `from_name` not in the closed list `image.png`, `edited.png` and the uploads (422: never a path); a refused refine leaves no `.from` or `.root`. A crash between the job and its two files leaves a job outside any session, never a session naming a missing job (the order as for `.set` and `.pair`).

## 7. What would show this wrong, and what is not known

* **Quality across rounds is not measured.** The result is a PNG (lossless), but the model works at about 1024 x 1024 and a round resizes its input (`tests/edit_pipeline_gpu.py`): a picture edited five times may drift or soften. Before slice 4 is called done: **one real session of five rounds on the GPU**, the first picture and the last looked at side by side, and the finding written here, good or bad.
* **The output size.** An edit's result is not always the input's size (seen: square results from non-square photos). Chained rounds would compound it; a fix belongs in `media` (restore the input's aspect), not in the studio, and is a separate piece.
* **Memory:** the server holds a request in memory (16 MiB ceiling, measured 11.8 MB after one 10 MB upload); a refine without an upload is a few hundred bytes. Not a concern.
* **Concurrent rounds.** Several refines queued from the same round are fine (the worker runs one job at a time); the tree shows them as branches.
* **Authority:** no new capability; the studio server still reads and writes only the data directory (`cancho authority` on `studio` should show the same rows; to be run when built).

## 9. The gallery (asked 2026-11-19; built and checked, see the end of this section)

**Asked for:** "the concept of a gallery, and a tag label: uploaded, generated, edited".

**What it is.** `GET /gallery`: every picture the studio holds, newest first, as a grid of tiles. Each tile has a **tag**, the picture, the job it belongs to (a link to `/jobs/N`) and, for a picture that can be refined, a *Refine* link (`/edit?from=N`). A filter row above the grid (`All`, `Uploaded`, `Generated`, `Edited`; `?tag=`) and 48 tiles a page (`?page=`).

**The tag comes from the file, so nothing new is stored and the old jobs get one too:**

| tag | which file | where |
|---|---|---|
| **uploaded** | `upload-N.*` (the first picture) and `upload-N-2.*` (the second) | `<data>/`, served as `/files/N/input1.*`, `input2.*` (#224) |
| **generated** | `out/N/image.png` (a picture made from a prompt, `kind` image) | `/files/N/image.png` |
| **edited** | `out/N/edited.png` (an edit, also a refine) | `/files/N/edited.png` |

An upload used by a refine is **not** listed twice: a refine's first picture is an earlier result, so it has no upload of its own. Frames and video files are not pictures of the gallery. A job's result appears only when the job is `done`; a failed job shows nothing.

**Where it meets the session.** The picker of slice 4 offers the gallery's pictures of that session (and may offer any picture: the limit is two). A tile's tag and job link tell *which round and which kind* a picture is, which is what a person needs to choose among them. The session page of slice 3 is the gallery filtered by session root, with the rounds in order.

**Refusals and limits.** `tag` is one of the three words (else 422); `page` is digits (else 422); a page past the end is empty, not an error; both need the token like any route. The listing reads the data directory (names only); no file is read until the browser asks for a picture.

**What would show this wrong, and what is not known.**
* **Weight.** The tile shows the picture itself (the studio makes no thumbnails: a decoder and a resizer exist in cancho, `docs/png-cho.md`, but a thumbnail store is its own piece). A result is about 1 MB; 48 of them is about 50 MB per page. Measured when built (the page's size and the time to first tiles in the browser pane); if it is too heavy, the page size drops, or thumbnails become slice 7.
* **Order across kinds.** Newest first means by job id; an upload and its result share an id and appear next to each other, upload first. Said here so it is not a surprise.
* **A job with both a result and uploads** shows up to three tiles (two uploaded, one edited); that is deliberate: each is a picture one can reuse.

**Checks planned (fake `media`, as the others):** one job of each kind and a two-picture edit give the right tags and counts; the filter returns only that tag; a refine's first picture is not listed as uploaded; a not-done and a failed job add nothing; `tag=bad` and `page=x` give 422; an empty data directory gives an empty grid with a sentence; no token gives 401.

**Built and checked (2026-11-19, `studio/gallery.cho`).** `GET /gallery[?tag=][&page=]` as designed: the tag from the file, newest job first (within a job: the uploads, then the result), 48 tiles a page with *Newer* and *Older*, a filter row, the tile's job and prompt, *Refine* on a result. The tiles reuse the job grid's styles; the tags are coloured (edited and generated in the accent colours, uploaded grey). A *Gallery* place is in the header of every page. `/gallery` is in `studio/openapi.json` (a check requires every route to be). 14 new checks in `studio/check.sh` (fake `media`): the number of tiles of each tag equals the files (uploads; done jobs' `edited.png`; done jobs' `image.png`), read across all pages; a failed job's `edited.png` is not listed; a refine's first picture is not an upload; a tile's `src` is the file the job page serves; a result offers Refine and an upload does not; 4 refusals (unknown tag, page not digits, 5 digits, mixed); a page past the end is empty with a sentence, status 200; no token 401; with 50 more uploads a page holds exactly 48 and offers Older, page 2 offers Newer, the pages together hold every upload once, and the newest upload leads page 1.

**Measured, looked at** (the studio on this branch in the browser pane, a copy of the earlier jobs' data): 25 tiles, 25 pictures, **13.6 MB** in all (about 0.5 MB a tile; uploads are JPEGs of a few hundred KB and results are PNGs of about 1 MB), so a full page of 48 would be about 26 MB, **half of the 50 MB estimated above**. The pictures arrive as the page is scrolled (`loading=lazy`); in the first screenshot the tiles were still empty, a second one a moment later showed them. The tags read clearly; the picture fills its tile, cropped to 16:9 (a portrait photo loses its top or bottom in the tile; the job page shows it whole). **Not done:** thumbnails (a smaller file per tile) would cut the weight, not needed at this size; filtering by session waits for slice 3; the gallery does not list the frames of a video, nor a video.

## 10. One menu, sessions, a library and a picker (asked 2026-11-19, designed)

**Asked for:** slice 3 (the session page); in the gallery, upload a picture; everywhere a picture is needed, choose it **from the gallery or upload one**; and merge the menu (Studio, Edit, Cases, Comparisons, and now Gallery and Jobs) into one or two places with a better UX.

### 10.1 The menu: two places and tabs

Six items in the header is too many, and they are two ideas: *making* and *looking back*. Two places, each with a row of tabs under the header:

| place | tabs (the old items) |
|---|---|
| **Create** (`/`) | Generate (the old Studio page: video and image) - Edit a picture - Cases |
| **Library** (`/gallery`) | Gallery - Sessions - Jobs - Comparisons |

No route changes: every old URL still works, only the header differs (the open tab is marked, the place that holds it is marked). The page of `/` is the cancho-ui island and takes its header from `results.decorate`, so it gets the same header. *Why not one page with everything:* the Generate page is a cancho-ui island and the rest are server-written pages; merging them would move one into the other for no gain. The tabs give the same effect (one place, one click) and keep each page as it is.

### 10.2 Slice 3: sessions

`GET /sessions` lists the sessions, newest first: a card per root with the first picture, the latest result, the number of rounds and the state of the last. `GET /sessions/ROOT` is the session: a row per round (inputs, result, prompt, seed, state, links), a round that came from an earlier round indented under it, and the refine form underneath (the picker of 10.4). A session is the jobs with one `.root` (section 3). A job with no `.root` file (made before slice 2, or by the API) is its own session of one round; `/sessions` lists those too, so nothing is missing.

### 10.3 The library: a picture with no job

A person should be able to put a picture in the gallery without making a job. **`<data>/lib/L<n>.<jpg|png|webp>`**, written by `POST /gallery` (multipart, `image`, up to 15 MB; the extension from the first bytes, as `/edit` does); the number is the line count of an append-only `<data>/lib.index` (the queue's way; the server is the only writer). Served as `/files/L<n>/picture.<ext>` (the `file_info` of the other pictures, with an id that is `L` and digits and the closed names `picture.jpg|png|webp`). Listed by the gallery with the tag **uploaded** and the job link replaced by "library". Refusals: not a picture (422), none (422), over the limit (413), no token (401), a foreign Origin (403): the gate `/edit` already has.

### 10.4 The picker

Every place that asks for a picture (the Edit form, each Cases card, the refine form) gets, per picture, **the file input and, beside it, "or choose from the gallery"**: a `<details>` with the most recent pictures as radio tiles (name `pick1` / `pick2`). No JavaScript. The value is `j/N/NAME` (a job's picture: `edited.png`, `image.png`, `input1.*`, `input2.*`) or `l/L<n>` (a library picture). **The server resolves it**: N digits, NAME in the closed list, the file there (and, for a result, the job done); the path is built by the server; nothing is copied. A file uploaded in the same request wins over a pick of the same slot. `from` (a refine) stays and means `pick1=j/N/<its result>`.

`.from` then names every picture: `N NAME` for a job's file, `L<n>` for the library, `upload` for a file sent with the job. The job page shows them all. A pick of a result stays in that result's session (`.root` of its job); a pick of an upload or of the library starts a session.

*Costs, said now:* the file inputs can no longer be `required` (either an upload or a pick will do), so **the browser will not stop an empty submit; the server's one-line 422 is what the person sees**. Cases has six forms and two pickers each: 12 recent pictures per picker (not 24) keep that page's markup to about 100 KB; the images are `loading=lazy` inside a closed `<details>`, so none loads until opened.

### 10.5 Order of work and what would show it wrong

A) the menu and slice 3; B) the library upload and the picker. Each its own PR with its gate. The menu change must not break a page: the existing checks that read headers (`aria-current`, the places) are updated where they counted the old links, and **each update is named in the PR**, not hidden. For B: a pick of a failed job's file, of a name outside the list (`input3.png`, `../x`), of a library id that is not in the index, and a pick of a video job all 422 and leave no file; a pick plus an upload of the same slot uses the upload.

## 13. A prompt over several lines (found by use, 2026-11-19)

**What happened.** Refining from the session page (and any form with a text area) failed with `{"error":"the prompt has no control characters"}` when the instruction had a new line: a browser sends a new line in a text area as CR LF, and `POST /edit` refused every byte under 32. The checks only ever sent one-line prompts, so none saw it (the lesson of `docs/media-cho.md` section 10 again: a check is only as good as the form it sends).

**Fixed.** The prompt and the note of `POST /edit` may hold CR, LF and tab; each run of them is written as **one space** (the instruction goes to the model and the argument list as one line, with no trailing space), and every other control character, NUL included, is still refused. A prompt of only new lines is 422 (it is empty once flattened). **Checked:** four new checks send CR LF the way a browser does (a refine of a result, a case's note with a new line, only new lines, and the session page's refine form).

## 14. One picture, several others: one edit each (asked 2026-11-19; built)

**Asked for:** "in the clothes case, one initial model and several clothes: try these 4 clothes and generate 4 edits; the same for decoration". **Makes sense:** yes, with two honest limits. Each edit is a separate GPU job of about two minutes and a half on this machine (measured: jobs of this kind took about 100 s each), so five garments are about twelve minutes, one after the other (the worker runs one job at a time); and the model does not always change an outfit that already matches the garment (section 8's tip), so the same instruction for every garment can leave one unchanged.

## 16. The describer: a small vision model writes the description (asked 2026-11-19; built)

**Asked for:** "support it with the small model": that a library picture added with no description get one written for it, so that the search of section 15 finds it.

**Which model, and why not cancho-gpu.** cancho-gpu has no model that writes text about a picture (its Qwen work is text-only training of 0.5B and 1.5B; the edit pipeline's vision-language encoder only makes conditioning for the image model, in torch). The studio already talks to Ollama for its prompt rewriter, and Ollama on this machine has **`qwen3.5:4b`** (3.3 GB, capabilities: vision). **Measured** (2026-11-19, `/api/chat`, one picture each, once): the green quilted jacket: "green quilted jacket with diamond pattern and side pockets" in 3.3 s with the model loading (2.3 s of it); a person in a white T-shirt (823 KB PNG): "A woman with dark hair wearing a blank white t-shirt and blue jeans against a beige background." in 2.1 s; another, 1.6 s. Accurate to a reader; **not a measurement of quality** (three pictures, one run). A native model is a separate, large piece of work.

**What was built.** `studio/describer.cho`, a **separate program** (`studio_describer <data-dir> <model> [--every s]`), started by `scripts/studio-up.sh` beside the server and the worker unless `STUDIO_DESCRIBE=off`; `STUDIO_DESCRIBE_MODEL` names the model (default `qwen3.5:4b`). It is separate, not a worker option, because the worker's arguments are positional and the describer needs no GPU, no `media` and no signals. Every pass (10 s): **if a job is queued or running it does nothing** (the GPU is the jobs'); else, for up to **three** library pictures (newest first) that have **no `lib-N.txt` and no `lib-N.tried`**, it asks the model through `rewrite.ask` (the rewriter's own call: `POST /api/chat`, no stream, no thinking, `keep_alive` 0 so the model is unloaded at once, no tools) for **a plain comma-separated list of words** (see the end of this section: first written as one short line, changed the same day), cuts the answer to **200 bytes** at a word, and writes it as `lib-N.txt` with the marker `lib-N.auto`. The gallery tile says **(auto)** after such a description; search finds it like any other. A description a person typed (written with the picture, before it is listed) is **never touched**. The picture goes to 127.0.0.1 and is not kept.
* **Cannot be described** (an unusable answer: empty, over 1,000 bytes or unclean; a file gone, too small or over 12 MiB): marked `lib-N.tried` and **not asked again**.
* **Cannot be asked** (Ollama not running or not answering in 180 s, or answering with an error such as a model not pulled): nothing is written and the **next pass tries again**; the pass stops at the first one.
* **`cancho authority`** (checked by the script): `net_out("127.0.0.1:11434")` is the only network row; no other programs, no foreign code, no signals; it writes files and reads its arguments.

**Checked.** `studio/describe_check.sh` (22 checks, 21 when first written; with the rewriter's stand-in for Ollama, one more of its modes added, `mid`: 300 bytes of words; the programs are built from copies in which the port and the 180 s deadline are replaced, and the script checks the copies differ from the real files only by those): the authority report; an undescribed picture gets the answer and the marker; a typed description is untouched; what is sent (model, a picture, no stream, no thinking, unload, no tools, the question); three at most a pass and the rest in the next; nothing while a job is queued, and described once the queue is empty; the cut to 200 at a word; an empty answer and one over 1,000 bytes are marked tried and not asked again; an error from Ollama, no Ollama, and no answer in time write nothing and are retried (an Ollama that comes back describes the picture); a gone file is tried and a bad index line skipped; **a mutant** (the describer that no longer looks for an existing description) overwrites a typed one, so the check can fail. `studio/check.sh`: one new check (a description with the marker says `(auto)`, a typed one does not). The rewriter's own script (68 checks) still passes with the stand-in's new mode. **Neither script is run by `scripts/gate.sh`** (it never was: the gate runs the compiler's tests and the `media` ones); run them with the commands at the top of each.

**Once for real** (the studio on this branch, Ollama with `qwen3.5:4b`): started with the describer on, three pictures added through `/gallery`, none with a description but one with `my own words`: within about ten seconds the jacket was "Green quilted jacket with diamond pattern, high collar, and side pockets on white background." and the JPEG "Young woman in white t-shirt black jeans and sneakers standing against yellow background.", both marked (auto) in the gallery; `my own words` was left as it was.

**Not done:** a button to describe again, or to replace an automatic description with a better one; no editing of any description; the library pictures that already exist get described by the first pass after the studio restarts with this build (nothing asks the person first: **every undescribed library picture is sent, in turn, to the local model**); job pictures are still found by their instruction, not described; the quality over many pictures and the 4B model's mistakes (it can name a colour or a garment wrongly) are **not measured**: an automatic description is a guess, which is why it says (auto).

**The prompt, compared and changed (2026-11-19).** The first prompt asked for one short line; reading its output on eight openly licensed pictures (CC0, public domain or CC BY, from Openverse; Wikimedia Commons refused further requests with 429) showed one wrong detail ("watch in pocket": the watch was on the wrist), words nobody searches for ("serene", "majestic"), and **different text for the same picture on different runs**. Three prompts were run once each over the same eight pictures with the same model (outside the studio: Ollama's `/api/chat`, no options, so Ollama's default temperature; the describer's real request uses 0.3), and 15 searches were simulated over each text (a word counts when it finds the picture it names): **A, one short line: 8 of 15; B, a plain list of words (each main object or garment with its colour or material, then the setting; "no adjectives like serene or beautiful, no verbs, at most 20 words"): 11 of 15; C, a sentence plus 8 to 12 keywords with synonyms: 12 of 15, but its keywords sometimes ran into the sentence, it made two descriptive errors ("licking paw", "embroidered"), and its longest text was 271 bytes, past the 200-byte limit.** B was chosen: shorter, cleaner, as accurate as A or more, and inside the limit.

**What changed with it.** `describer.cho` asks B's question, with the same system message as before; `rewrite.ask` and `rewrite.body_of` got a `cold` argument that sets the **temperature to 0 instead of 0.3** (the describer passes `true`; the rewriter and `media rewrite` pass `false`, so their requests are as before: a check in `studio/rewrite_check.sh` says so). **Measured with the real describer** on the eight pictures, two runs in two libraries: **the texts were identical in all eight pictures** (so the same picture gets the same words), 67 to 125 bytes each, and **10 of the 15 searches found the right picture** (the earlier one-run test of B found 11: the difference is the sampling noise of such a small test; do not read it as better or worse). Reviewed against the pictures: six of the eight lists name what is there (including, for the Japanese room, the folded towels, the microwave and the washing machine), **one has a wrong object** ("beige plant pot" for sneakers with a plant growing out of one), and one has a small colour slip (a golden retriever's fur as "brown"). **The synonym gap is not closed:** "bike" (the picture says bicycle), "shoes" (sneakers), "denim" (jeans), "lamp" (chandelier) and "refrigerator" still find nothing, and that is the main thing to do next (a small word list of synonyms in the search, or a second prompt that adds one common synonym; neither is built or measured).

## 17. Synonyms and words in any order in the search (asked 2026-11-19; built)

**The gap.** After the describer's prompt was changed (section 16), 5 of 15 test searches still found nothing because the picture's word was not the person's word: `bike` for `bicycle`, `shoes` for `sneakers`, `denim` for `jeans`, `lamp` for `chandelier`, and `refrigerator` for a picture whose list did not hold it. A model prompt that adds synonyms was tried first (prompt C of section 16) and was worse in other ways, so the fix is in the search, where it works on **every** description and on the instructions of job pictures, needs no model, and cannot make an answer up.

**What it does** (`picks.query_hit`, used by `picks.matches`, so by the gallery's `?q=`, the search of `/cases` and every picker). A picture is found when its text holds the search text as it is (as before), **or when every word of the search is there, in any order**; each word counts if the text holds it (as before, inside any word: `sneaker` finds `sneakers`) **or holds a synonym of it as a whole word** (a letter or digit on either side does not count; one trailing `s` is allowed). Synonyms are the groups in `picks.groups()`, a starting list of **true synonyms**: bike / bicycle / cycle; shoe / sneaker / trainer / footwear; jeans / denim; couch / sofa / settee; lamp / chandelier / lantern; fridge / refrigerator; tv / television; pants / trousers; sweater / jumper / pullover / sweatshirt; tshirt / t-shirt / tee; dress / gown / frock; hat / cap / beanie; dog / puppy / canine; cat / kitten / feline; car / automobile; sea / ocean; phone / smartphone; rug / carpet; painting / artwork. A plural is the same word. Words in no group are only themselves. **Chosen not to be synonyms** (they change what an existing search returns, or are too loose): jacket and coat, shirt and t-shirt, picture and artwork, mobile and phone.

**A flaw found while building it, and fixed:** the first version looked for the group's words as substrings, so `hat` would have found `that`, `cap` `landscape` and `cat` `chat`. Group words now match **only as whole words**; the word a person types still matches inside words, as it always did (`hat` still finds `that`: unchanged, and said here so it is not a surprise).

**Measured, with the real search** (a test studio whose library held the eight test pictures with the exact words the real describer wrote for them, section 16): the same 15 searches find the right picture **14 of 15 times, against 10 of 15 without synonyms**, each time that picture alone. The one miss is `refrigerator`: the picture shows a fridge but the model's list does not name it, which no search can fix. Also: `white shoes` and `shoes white` both find the sneakers; `table lamp` finds the dining room with the chandelier; `cycle` finds the bicycle; `hat`, `cat`, `couch`, `jumper` and `tv` find nothing (no such picture), so no false hits. Eight pictures and one list of searches I chose: it shows the mechanism works, not how often a person's word will be in a group.

**Checked** (`studio/check.sh`, 8 new checks): bike, shoes, lamp and couch find a bicycle, sneakers, a chandelier and a sofa; both ways round, plural, capitals and other members of a group; a word of no group is only itself and a synonym does not find an unrelated picture; jeans and denim find the denim jeans and **a jacket is not a coat**; several words in any order must all be there (`jacket green`, `dress red`; `green bicycle` finds nothing), a phrase still works, and extra spaces do not matter; a synonym is a whole word (`beanie` finds the two pictures with the word hat and not `that` or `landscape`); a job's picture is found by its instruction with the same rules; the Cases pickers use them.

**Not done:** the list is mine and small (19 groups, English only); there is no way to add a group without editing `picks.cho`; no accent folding; no stemming beyond a trailing `s` (`jackets` finds `jacket` through the plural; `running` does not find `run`); the search is still a scan of every picture (section 15 measured that: about 0.23 s for 3,000 jobs and no hit).

## 19. Groups of pictures, and Cases split into tabs (asked 2026-11-20; built)

## 21. A finished job no longer leaves `work/` behind (asked 2026-11-20; built)

**Why it was kept.** Nothing resumes from `out/N/work` and no option needs it: `build/media` makes `DIR/work` (`media/media.cho`, `media/clip.cho`) and hands it to the stage drivers as their scratch directory (`tests/t2i_pipeline_gpu.py`, `tests/edit_pipeline_gpu.py`: the stage files, `edit_work/`, `vae_work/`, the `.npy` and `.f32` between stages); only the logs and results are read afterwards. The worker's own tidy (docs/studio.md) existed since slice 2 but cleared only **one level** of subdirectories, so the files in `work/edit_work/` and `work/vae_work/`, where the gigabytes are, were never reached.

**Measured** (this machine, `scripts/media image`, 8 steps, results `image.png` and `prompt.txt`):

| job | `out/N` | of it `work/` | `work/edit_work` | `work/vae_work` | files in `work/` |
|---|---|---|---|---|---|
| 512 x 512 | 1.1 GB | 1.1 GB | 589 MB | 536 MB | 248 |
| 1024 x 1024 | 3.1 GB | 3.0 GB | not split | not split | not split |

Both before the change; the results are `image.png` (a few hundred KB) and `prompt.txt`. An edit job is in the 2 to 7 GB the studio's owner saw; I did not run one here.

**What changed.**
* `scripts/media` (shell, because the pinned compiler cannot remove a directory: `unlinkat` without `AT_REMOVEDIR`): with `CANCHO_MEDIA_CLEAN_WORK=1` it removes `DIR/work` (`DIR` is the argument after `-o`) when the job exits 0. **Without the variable nothing changes**: the command line keeps `work/`, which is the explicit way to keep it for debugging. A failed job keeps it, to look at. Both the cancho program and the Python fallback are covered.
* The studio's worker sets `CANCHO_MEDIA_CLEAN_WORK=1` in the environment it gives every job, so removal is the default for the studio. It has no switch to turn that off; to keep `work/` run `scripts/media` by hand.
* The worker's tidy now goes **all levels** down (`clear_tree`, eight deep; a link is neither followed nor removed), so even when the wrapper is not the one that ends the job, no file is left.
* **At start** (`sweep`, under the lock, after `recover`): every job in the queue whose state is `done` is tidied as after a run, and every one that is `failed N` (a dead worker's `failed 255` included) loses `work/` only, its other files staying. A job with no state, or not in the queue, is never touched; a job that is running is not either (the worker is the only one that starts jobs, and it is not between jobs). Silent: no log line.

**Left, stated.** The worker cannot remove a directory, so for a job that ended before this change, or one that failed, the empty `work/` tree remains (about 4 directories); only `scripts/media` removes `work/` itself, and only for a job it ran with the variable. A failed job's `work/` files stay until the next time a worker starts.

**Checked** (`studio/check.sh`: 586 ok and the one failure that is also on main): a done job has no file in `work/` at any depth and its results stay; the log's count; a failed job keeps `work/` while it is the run that failed and loses it (and only it) at the next start; a done job from before the change is tidied; a job not in the queue is untouched; the job sees its `work/` while it runs; the wrapper keeps `work/` by default, removes it with the variable on success, keeps it on failure.
