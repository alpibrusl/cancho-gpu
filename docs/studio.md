# cancho-studio: a web app to make and edit images and videos (design, 2026-11-16)

> **Status: design; slice 1, the queue and the results page are built (see "Built so far").** Written from reading `cancho-web`, `cancho-ui` and `cancho`'s `std.process`; the claims below say what was read and what was not run.

> Later notes: `docs/studio-variations.md` (variations of one request, the CLI's parameters, the pages' style) and `docs/studio-design.md` (a visual design to apply, and what islands can and cannot do here).

## Running it

```
CANCHO=<the pinned cancho> UI=<the cancho-ui binary> scripts/studio-up.sh [PORT] [DATA_DIR]
```
`scripts/studio-up.sh` (default port 8090, data in `build/studio-data`) builds what is missing, starts the server and the worker and prints `studio: http://127.0.0.1:PORT/?token=...`; open it, Ctrl-C stops both; `--rebuild` as the last argument builds again. A job needs the Metal session and the weights (`scripts/media doctor`); the pages and the API work without them. Do not point it at the data directory of another running studio.

## Goal

A page on `localhost` where one types a prompt (and, for an edit, names a photo), starts a job, sees it progress, and opens the result. It is the `media` command line (`docs/cli.md`) with a browser in front: the models, the limits and the one-GPU-job lock are the CLI's, unchanged.

## Parts

* **Server** (`studio.cho`, on the `http.server` package, not `cancho-web`'s typed API: the routes are matched by hand, so the OpenAPI document is **not generated** from them. *Corrected 2026-11-16; the first design said "a typed API declared once (and so its OpenAPI document)".* It is `studio/openapi.json`, written by hand and held to the server by `studio/check.sh`; see "Built so far"):
  * `POST /api/jobs` `{kind: "video"|"edit", prompt, image_path?, frames?, size?, seed?}` -> `202 {id}`; `422` as `problem+json` for what `media` would refuse (sizes not multiples of 32, over the measured limits).
  * `GET /api/jobs/{id}`: `{id, state}` (`queued|running|done|failed C`). *Corrected 2026-11-16:* no stage line, seconds elapsed or file list; the results page shows the files. *Corrected 2026-11-17:* there **is** now `GET /api/jobs`: `{running, queued, jobs:[{id, state, kind, prompt}]}`, the 50 newest, newest first (`results.api_list`, the same read of `queue` as the HTML list); the main page shows recent jobs through a frame on `GET /recent` instead (docs/studio-design.md section 6), not through this list.
  * `GET /files/{id}/{name}`: `edited.png`, `video.mp4`, `video.gif`, with the right `Content-Type`; names are from a closed list, never a path from the client.
  * `GET /api/models`: the registry of `tools/media.py`.
  * One job at a time (the CLI's `gpu.lock` already refuses a second); the server queues, it does not run two.
* **Worker**: the server spawns `scripts/media` with `exec_spawn` (`std.process`; arguments as a `\0` list, output to the job's log). *Corrected 2026-11-16:* an `Exec` narrowed to the script's prefix was not possible (`narrow` takes a literal and the script is an argument); what was built is `exec_spawn_under` (see "Built so far"), and the report names `exec_under`, not one program. The prompt travels as an argument entry, never through a shell.
* **Page, `cancho-ui`** (`studio.cui`): a form (`TextField`, `Button`), a job list refreshed by `every N Event`, `net.post` to create a job, `net.get` to read it. `requires Network; requires NetworkWrite;`.

## What was read that decides the design

1. **`net.post` sends JSON text and `FileField` reads a bounded text file** (`cancho-ui/docs/file-upload.md`: "not done (binary, multipart)"). A photo cannot be uploaded from the page. **Decision for the first version: `edit` takes a path on the machine the server runs on** (this is a local tool; the same as the CLI). The server refuses a path that is not a regular readable image file, and never copies it anywhere but its own working directory. Upload is a later slice and needs a cancho-ui change.
2. **`Image`, `Media` and `Link` take a literal `src` / `to`, checked when the page is built** (read on cancho-ui `main`, 12e57c6, 2026-11-16: `crates/cancho-ui-ir/src/media.rs` "`src:` of an Image is a text literal, the path of a file of the site", `media-src-invalid`, `asset-missing`, 20 MB cap; `structure.rs` "`to:` of a Link is a string literal ... a text that reads state is not a link"). A job's result, which exists only after the page was compiled, cannot be shown or linked from a cancho-ui page. **Decision, route 3: the results page is HTML the server writes** (`GET /jobs/{id}`: the prompt, the stage, an `<img>` or a `<video>` of `/files/{id}/...`). The cancho-ui page (form and job list) links to it by a navigation the browser does, not by a `Link`: see "What cancho-ui would need". cancho-ota-ui was checked: its console (`ui/trip.cui`) is text only, so it shows nothing to copy for pictures; its server / worker split is what this design takes (the server queues and is the one writer, a worker alone does the expensive work).
3. **cancho has no `exec` that the compiler lets a library hide** (`std/process.cho`): the caller spawns. That is what we want here.
4. **`cancho-web` is on the `http.server` package**, one thread and a `Poller`, no FFI. A long job must not block the poll loop: the server starts the child detached (`exec_spawn_detached`), and each request reads the child's status file, so no request waits on the GPU.

## What cancho-ui would need to work with photos

Each is a gap read in the source, not a measured failure; none is built. In the order they would unblock the app:

1. **A dynamic source for `Image` and `Media`**: `src:` from a `String` in state (a `net.get` answer or a job's `result` field), with the rules the literal has today kept as run-time ones: a closed set of extensions, a same-origin path only (as `net.get` is), `alt:` still mandatory, `ratio:` still declared before load. Build-time `asset-missing` cannot apply; a failed load needs a state of its own (`on Error`).
2. **Binary upload**: `net.upload(url, file)` as `docs/file-upload.md` sketches (bytes as the body, never read into a JavaScript string, a handle type that is not a `String`, its own capability line), with `FileField` accepting `image/*` and giving the handle plus name and size. Today `FileField` reads UTF-8 text and `net.post` sends JSON.
3. **A `Link` whose `to:` is a run-time string**, same-origin only, for a file the page cannot embed (a download of `video.mp4`).
4. **A local preview of the chosen photo** (`Image { src: <the handle> }`), so the page shows what is about to be sent: a revocable object URL, never leaving the page.
5. **Replay support**: `cancho-ui test` traces would need scripted answers for the upload and the dynamic source, as `net.post` has.

Until 1 and 2 exist: `edit` takes a path on the server's machine, or a picture sent to the server's own `/edit` form (see "Built so far"), and the result is shown by the server's own HTML page.

## Safety

* Bound to `127.0.0.1` only, **and** (`studio/auth.cho`, 2026-11-16) every request must pass four checks in this order: `Host` is `127.0.0.1:<port>` or `localhost:<port>` (else 403: a name that resolves to loopback, DNS rebinding); `Origin`, when there is one, is `http://` plus such a host (else 403: a request made by another site's page); the **token** is a bearer header or the cookie `studio` (else 401); a POST says `Content-Type: application/json` (else 415: `text/plain` and forms are what a page can send without asking). The token is 32 hex characters from `/dev/urandom`, made when the server starts and printed as a URL, `http://127.0.0.1:<port>/?token=...`, as Jupyter does; opening it is the one place a query token is taken (`GET /` only): the server answers `302 /` with `Set-Cookie: studio=...; HttpOnly; SameSite=Strict; Path=/`, so the token is not left in the address bar or the history, the page's own requests carry the cookie and another site's do not. It is not stored; a restart makes a new one (the browser keeps the old cookie and gets 401 until the new URL is opened). The comparison does not stop at the first different byte. The worker has no network and needs none.
* The prompt is data: a `\0` is refused (`std.process.add` returns 22). Output directories are `<jobs>/<id>/`, `id` made by the server.
* `edit`: the photo is read, never committed or uploaded; the server logs the path's basename, not the prompt.
* The page requires `Network` and `NetworkWrite` and nothing else; `cancho-ui authority` lists them.

## Built so far (2026-11-16)

* **Slice 1**: `studio/studio.cho`, the loopback server (page, `/api/models`).
* **The queue, slice 2** (checked 2026-11-16): `studio <port> <absolute data-dir>` takes `POST /api/jobs` `{kind: video|edit, prompt, frames?, size?, seed?, image? (edit)}`: the shape is checked (kind, prompt 1-1000 bytes, frames 1-129, size `WxH`, seed, an edit's image path), the arguments for `media` are written with `std.process.add` (which refuses a NUL) as `<data>/N.argv` after a `--` (so a prompt starting with `-` is a prompt), and N is appended to `<data>/queue`; answer `202 {"id":N}`, else `422`/`500` with a one-line reason. `GET /api/jobs/N` answers `queued|running|done|failed C` (404, 422). `studio_worker <script> <home> <data-dir>` drains the queue once and exits (run it in a loop, as cancho-ota's worker is): each id without `<id>.state` runs, one after another, `<id>.log` has the output, ids that are not 1-9 digits are skipped. The server is the only writer of `queue` and `*.argv`; the worker of `*.state` and `*.log`; `media` writes `out/<id>/`.
* **Checked** by `studio/check.sh` (27 checks, a fake `media`, no GPU): metacharacters and a leading `-` reach the script as one argument; refusals; queued, done, `failed 3`; a job with a state is not run again; a relative data directory is refused. **And once for real** (not in the script: it needs the GPU): `POST {"kind":"video","prompt":"A red fox running through snow","seed":1}`, then the worker on `scripts/media`: `done` in 27 s, `video.mp4`, `video.gif` and 17 frames in `out/1/`. The edit path was run only against the fake script; `media edit` refuses a missing image (checked by hand: `no such image`).
* **The results page** (checked 2026-11-16, 44 checks in `studio/check.sh`): `GET /jobs/N` is HTML the server writes (state; the `<video>` or `<img>` when `done`; a link to the log; refreshes every 5 s while queued or running); `GET /files/N/NAME` serves `edited.png`, `video.mp4`, `video.gif` or `log` of job N, a closed list: a path or another name is 404, an id that is not digits 422. Bytes arrive unchanged (`cmp` on a binary file). Opened in the browser pane with the real `video.mp4` of the earlier job: it decodes, 640x352, 1.06 s, no error.
* **Big files and `Range`** (checked 2026-11-16). `http.server` holds 64 KiB of output per connection and a bigger `respond` is cut and the connection closed (a 6 MB file arrived as 327119 bytes, measured). The package has its own way for big answers (`hold`, `stream`, `answer`: its `docs/http-server.md` section 14, `/big/<n>` in `examples/https_hello`), so `studio` uses it. **A stream is four integers and a path**, not a buffer: the ticket of the held request, the next byte, the byte to stop before, and the path in a 512-byte slot of an arena; each turn of the loop (20 ms while any is going) reads the next piece, at most what the connection has room for and 64 KiB, with `files.read_at` (`file_pread`, the file opened and closed for that read) and hands it to `stream`; `answer` with no bytes ends it. So up to **8 files go at once** and none is held in memory (the first version held one file whole, one at a time, and refused over 64 MiB; Safari asks for several ranges of a video at once, which that could not serve). `Range: bytes=a-b`, `a-` and `-n` are answered `206` with `Content-Range`; a range at or after the end, or the last 0 bytes, `416` with `Content-Range: bytes */N`; no header, another unit, a list of ranges, a spelling that is not a range or `b` before `a` get the whole file, `200`; every file answer says `Accept-Ranges: bytes` (`studio/range.cho`). Checked: 6 MB and 40 MB `cmp` equal, `Content-Length` right, two files on one connection, a range across the 64 KiB piece, a megabyte from the middle of 6 MB, 21 range cases, six downloads of 6 MB at once each equal, the server answers after. In the browser pane (Chromium, not Safari): the `<video>` asks for the file and gets `206`, seeking to 0.8 s plays, `bytes=0-1` gives 2 bytes with `Content-Range: bytes 0-1/104177`. **Not checked:** Safari itself (what it asks and how it reacts were taken from the RFC and from what is known of it, not run); more than 8 at once is `503` with `Retry-After`; a file that shrinks while it is sent ends short (the stream stops at a read of 0); `HEAD` is not answered. **Cosmetic:** `std.http.reason` has no 206 or 416, so the status line says `206 Unknown`; clients ignore the phrase, the fix is in `std`.
* **Tidying `out/N/`** (checked 2026-11-16, 64 checks, and on a copy of the real job's directory): `media` leaves its session's work files beside the results, 1.3 GB (`du`) for a 17-frame video: 346 files, 0.2 GB beside the results and 1.1 GB in a `vae/` subdirectory. After a job that ends `done` the worker removes them: the files of `out/N/` that are not `edited.png`, `video.mp4`, `video.gif` or `prompt.txt`, and the files of every subdirectory but `frames/` (the frames are a result: 4.9 MB). Result: 1.3 GB to 6.8 MB. It goes beneath a `Dir` handle (`open_dir`, `dir_remove`: the authority report now also names `dir_read` and `dir_write`), a link is never followed, and the log's last line says how many were removed. A failed job keeps everything (to look at). **Left:** the emptied subdirectory itself (`unlinkat` is called here without `AT_REMOVEDIR`, so a directory is not removed), one level deep only, and a list of kept names that is in this file, not read from `media`.
* **The page, `studio/ui/studio.cui`** (checked 2026-11-16, cancho-ui main b9745db): `cancho-ui check` passes; `cancho-ui test` replays `studio.trace.json` (14 steps, 29 checks: refused while the prompt is empty, a video job queued, `running`, `done`, no polling after it, an edit refused without a picture, started, and the server's `422` shown). It has the form (`Select` for kind, frames, size and seed; `TextField` for the prompt and an edit's picture path), reads `api/jobs/N` every 3 s while the job is queued or running, and requires `Network` and `NetworkWrite` only. The server serves it: `studio <port> <data-dir> <site-dir>` (`GET /` is `index.html`, `GET /app.js`, from `cancho-ui build studio/ui/studio.cui --page -o <site-dir>`), and `GET /jobs` lists the jobs newest first. **Once for real, in the browser pane:** the form, a video prompt, Start: `queued`, `running`, `done` (the worker with `--every 2` on `scripts/media`); `/jobs/1` plays the 640x352 clip (1.06 s); the worker tidied 346 files, `out/1` is 5.9 MB. Not judged: whether the clip shows the prompt (a paper boat in a rainy street gave a vehicle in a lit street; a distilled model at 17 frames and 640x352). **Gaps found:** (1) a `Link` cannot point to a route of the server (`link-file-invalid` for `jobs` and `/jobs`: it takes a file of this site or an absolute URL), so the page names `/jobs/N` in text: cancho-ui item 3 above, now measured; (2) the page's elements are replaced every 3 s by the schedule, the value and the focus survive (checked: new element, same value, focused), the caret position was not; (3) `PhotoField` now exists (cancho-ui 12.0r), but it gives at most 48,000 characters of base64, about 36 KB of JPEG, so a picture to edit would arrive far below the 1248x832 the model works at: the edit still takes a path on the server's machine; (4) `index.html` and `app.js` (31 KB and 42 KB) are still read whole and sent with `respond`, so they must fit its 64 KiB room: they do, only because they are small.
* **Auth** (measured 2026-11-16): *before*, on the server as it was, a POST with `Origin: http://evil.example` and `Content-Type: text/plain` was answered `202` and a job was queued (an edit's `image` is any path), and a `Host: rebinding.example` request was answered 200. *After*: 29 checks in `studio/check.sh` (no token, wrong token, wrong length, bearer, cookie, the login URL, the cookie's attributes, a token in the query anywhere but `/`, rebinding hosts, a right host on the wrong port, `localhost:<port>.evil.example`, a foreign `Origin`, `Origin: null`, `localhost.evil.example`, the attack with the user's own cookie and no job queued, `text/plain` and a missing content type: 415, two servers two tokens). In the browser pane: the URL with the token loads the page and leaves no token in the address bar, the cookie is not visible to JavaScript, the form starts a job; a page on `localhost:<port>` (another origin than `127.0.0.1`) that posts to the server with `credentials: include` is refused (cors blocked; a `no-cors` request reaches the server, is refused, and the queue is unchanged). **Not covered:** another user of the same machine who can read the server's stderr (the URL is printed there) or its process list is not stopped by it; the token is not rotated while the server runs; `GET` requests with a `no-cors` fetch carry no cookie either (`SameSite=Strict`), checked only for the POST.
* **The OpenAPI document** (checked 2026-11-16): `studio/openapi.json`, OpenAPI 3.1, 10 paths (`/edit` added with the upload), the two security schemes (bearer, cookie), the request and answer shapes and the refusals (401, 403, 415, 422, 404, 416, 503). The server answers `GET /openapi.json` from the site directory (404 without one). It is written by hand, so `studio/check.sh` holds it to the server both ways: a table of requests whose measured status must be listed under that path in the document (the refusals of every route, `206` and `416` on a file, a `422` for a bad id, the login `302`), every path the server matches must be a path of the document, the file must be JSON and every `$ref` must have a target. What this does not check: the *bodies* against their schemas (a field renamed in `jobs.cho` is caught only by the `POST` rows that send it), and the response headers; the `500` of `POST /api/jobs` (the queue unreadable) is listed but no request here reaches it.
* **The worker's `Exec`, narrowed** (measured 2026-11-16). *Before*, `cancho authority studio/worker.cho` said `exec("")`: any program anywhere. The path is not known at build time (it is an argument), and `narrow` takes a literal. `docs/processes.md` §4.14 of cancho built the answer: `exec_spawn_under(exec, dir, name, ...)`, a program that is a name in a directory opened once. The worker now splits `<script>` at its last `/`, opens that directory (`open_dir`, a `Dir`) and starts the script by its name beneath it. *After*, the report says `exec_under` and no `exec("")`. A script whose name is empty or has `..` is refused (exit 3) instead of trapping; so is a script with no directory or in one that does not open. Two consequences: the script now starts **with its own directory as the working directory** and `/var/folders/s5/pnld4xwd6m78ztb80vplzpjc0000gp/T//ed2.pl` is its bare name (the real `scripts/media`, which finds `../tools/media.py` from `dirname "$0"`, ran `--help` through the worker and ended `done`; checked by hand, not in `check.sh`, which uses a fake script), and the report says *which program* only as "one in a directory it was given": not which directory, and not that it is `scripts/`. The directory is bound once, so a link in it to a program elsewhere would run (cancho's own measurement, §4.14). `check.sh` holds the report (`exec_under` yes, `exec("")` no) and the refusals.
* **Editing a picture chosen in the browser** (measured 2026-11-16). `PhotoField` could not do it: it gives the program a JPEG of at most 48,000 base64 characters (about 36 KB, cut down until it fits) and the edit pipeline resizes its input to about 1024 x 1024 pixels (`tests/edit_pipeline_gpu.py` line 88), so the picture would be blown up from a thumbnail. The page cannot send bytes (cancho-ui's `net.post` is JSON text; binary `net.upload` is its "next step" and does not exist), so **the server writes a second page, `GET /edit`**: a plain `<form method=post enctype=multipart/form-data>` (the instruction, a seed, a file; no JavaScript), and `POST /edit` parses the multipart body in cancho (`studio/upload.cho`): parts found by their `name="..."` headers, the picture kept as `<data>/upload-N.jpg|png|webp` (the extension from the first bytes, never from the name or `Content-Type` the browser sends; anything else is 422), the job made by `jobs.create` as `POST /api/jobs` makes it (the same refusals), and the answer `302 /jobs/N`. **The body is held whole in memory**: the server's connection buffer went from 64 KiB to 16 MiB (a bigger request is the package's 413), instead of the streamed-body API (`limits`, `body_part`), which would also have turned a body split across two reads of any other route into a refusal. **Measured:** the server's resident memory is 1.4 MB idle and 11.8 MB after one 10 MB upload (the buffers are not touched until used, so 16 MiB is a ceiling and not a cost). Checked (`studio/check.sh`, 211 checks, 27 of them new, 18096): a 3 MB JPEG kept byte for byte, a PNG, a WebP; a prompt with a quote, a backslash, `;` and UTF-8 reaches the script as one argument; refusals (text named `.jpg`, no prompt, no picture, bad seed, prompt over 1000 bytes or with a control character, JSON sent to `/edit`, over 16 MiB, no token, a foreign Origin, a rebinding Host, multipart sent to another route), none of them queues a job or keeps a picture. And **once in a real browser** (the built-in browser: a PNG drawn on a canvas, put in the file input, the form submitted by its button): 276,976 bytes kept, a valid 640 x 480 PNG, the job queued, the browser landed on `/jobs/1`. Not done: **the Safari and phone pickers were not run**; the form's errors are the server's one-line JSON (a browser shows it as text); the picture stays in the data directory after the job (nothing deletes `upload-N.*`; it is the user's photo on the user's own disk, and `.gitignore` does not cover a data directory chosen by the user: keep it outside the repository); `POST /edit` is the one POST that is not JSON, so the `415` rule of the auth gate has this one exception, safe because it still needs the token, the Host and Origin checks first, and the cookie is `SameSite=Strict` (a foreign page's form carries none; checked: 403); a failure after the picture is written (the queue unreadable, 500) leaves it. The cancho-ui page says /edit exists in a line of text (a `Link` cannot name a server route).
* **Not done:** a link from the page to `/jobs/N` and to `/edit` (cancho-ui limitation).

## The log holds the job's errors (2026-11-19)

The worker started a job with its error stream thrown away (`Stdio::Null`), and `media` writes every refusal there (`media: ...`), so a job that was refused failed with **an empty log** and no reason on its page. The error stream now goes to `<data>/N.err` and, when the job ends, what it holds (at most 64 KiB) is added to the end of `N.log` under a line `stderr:`. A job that wrote no errors has the log it had. Errors therefore show when the job ends, not line by line while it runs. `studio/check.sh` has four checks (a refused job is `failed 2` and its log shows its output, then `stderr:` and the message; a job that ended well keeps its errors in the log too; a job with none has the log as before); with the copy disabled the log is `out: shout|` and the message is lost. The `N.err` file stays in the data directory.
